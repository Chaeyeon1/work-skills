# 결과 보고 (넘기기 전)

요청자가 모르는 동작이 하나도 남지 않게 한다. 말로 "됐다"가 아니라 실행 결과로.

1. **기능·케이스 뽑기.** 기억 말고 코드와 커밋(`git log --oneline`, `git diff <첫 커밋>..HEAD --stat`)에서 뽑는다: 분기, 기본값, 막는 조건, 오류 문구, 빼는 경우.
2. **README 넘김 내용.** 없으면 쓰고, 있으면 고친다:
   - 무엇을 위한 것인지 한두 줄 / 실행 방법 / 기능·케이스 표 / 규칙별 확인 결과(규칙 번호 → 명령 → 결과) / 남은 한계(🔴🟠🟡)
   - 파이프(`|`)가 든 명령은 표 칸에 넣지 말고 표 아래 코드 블록에 둔다(표 칸에서 `\|` 로 깨져 그대로 따라 칠 수 없다)
3. **실행 방법 따라 하기.** 방금 쓴 README 의 실행 방법을 처음 보는 사람처럼 위에서부터 그대로 실행한다. 막히면 README 를 고친다. 끝나면 README 를 `보고서: 넘김 내용` 으로 먼저 커밋한다(4번은 깨끗한 트리에서 시작해야 한다).
4. **수정 전/후.** 작업 트리가 깨끗할 때만(아니면 먼저 커밋. 결과물을 다시 만들어 생긴 변경도 되돌리고 시작). 가장 중요한 규칙 하나를 잠시 끄고 결과를 `.verify/` 같은 git 이 무시하는 폴더에 만든 뒤, **완료 조건의 확인마다** 달라졌는지 표로 적는다(`| 확인 | 켰을 때 | 껐을 때 |`, NOTES '확인' 아래). 숫자 합계만 보지 말고 그 규칙이 걸리는 행을 직접 비교한다. 끝나면 `git checkout -- .` 로 되돌리고 `git status` 가 깨끗한지 보여 준다. 어느 확인으로도 달라지지 않으면 그 규칙을 확인하는 수단이 없다는 뜻이니 '남은 한계'에 적는다.
5. **문서와 실제가 다른 곳.** NOTES·README·PLAN 의 문장 중 코드·커밋·실행 결과로 확인되지 않는 것을 찾아 고치거나 [추정] 을 단다. 사용자가 하지 않은 확인을 적지 않는다.
6. **커밋.** 4·5번에서 바뀐 NOTES·README 를 `보고서: 끄고 비교 — 확인: …` 으로 커밋한다.

마지막: 바꾼 파일과, 사용자가 화면에서 직접 볼 것(`직접 확인:`), 요청자에게 보여 줄 요약 세 줄. 요약의 숫자·사례는 기억 말고 방금 돌린 실제 출력에서 옮긴다.
