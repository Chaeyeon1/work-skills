# 넘기기 전 설명 준비

> 평소에는 따로 커맨드로 두지 않았다. 리뷰·인수인계 전에 머릿속으로 하던 준비(왜 이렇게 했나, 숫자 근거, 약점)를 이번에 스킬로 만든 것이다.

목표: 결과물을 넘긴 뒤 누가 "왜 이렇게 했어요?"라고 물어도, 화면을 보지 않고 내 말로 답할 수 있게 한다.
답안 문장은 대신 쓰지 않는다. 재료(근거 위치와 짧은 명사구)만 준다. 지어내지 않고, 하지 않은 확인을 했다고 쓰지 않는다.

## 읽을 것 (필요한 만큼만)

- `git log --reverse --format='%h %ad %s' --date=format:%H:%M`
- NOTES.md: 요청자 대화 · 결정 · 확인 · 남은 한계
- AGENTS.md: 확정된 규칙 · 확인 안 된 것 · 기각한 대안
- PLAN.md: 다시 정의한 문제 · 완료 조건 · 우선순위
- 핵심 코드: 규칙 주석(`# 규칙 N`)이 있는 곳 위주. 파일 전체를 출력하지 않는다

## 내놓을 것 (터미널에. 파일은 만들지 않는다)

0. **지금 고칠 것** (있으면 맨 위). NOTES·PLAN·제출 문서 전부의 문장 가운데 코드·커밋·실행 결과로 확인되지 않는 것, NOTES 에서 [추정]·미확인이던 숫자가 제출 문서에 표시 없이 쓰인 곳. 문장 위치(파일:줄)와 어긋나는 근거를 한 줄씩. 예: "NOTES 확인: '화면에서 확인함' — 화면 확인 기록 없음". 없으면 "없음".
   - **내가 정하지 않은 이름**: 문서·화면·코드에 쓰인 모듈·상태·화면 이름 가운데 NOTES '결정'에 사용자 출처가 없는 것. `이름 — 쓰인 곳(파일:줄) — 코드 기준 뜻 한 줄`. 사용자가 내 말로 바꾸거나 정의할 때까지 여기 둔다.
   - **제출 문서의 가정·한계 칸**: README 가 정한 제출 문서에 가정·한계·제한 칸이 있으면 NOTES '남은 한계' 줄마다 `한계 → 제출 문서 파일:줄 / 없음 / 모순` 한 줄씩(하지 않은 확인·빌드 줄 먼저). 제출 문서의 '확인한 것'은 주장 하나씩(한 줄에 이어 쓴 것도 나눠) 요청자 답 시각을 대고, 요청자가 그 주장을 직접 말하지 않았거나 답이 '모름'·'기준 없음'이면 모순.

1. **물을 만한 질문 6~8개.** 종류마다 하나 이상:
   - 무엇이 더 나은 결과인지 판단한 기준과 방법, 더 강한 방법(예: 전체 최적화) 대신 이걸 고른 이유와 포기한 것(기준 순서를 바꾸거나 더 단순한 방법으로 같은 자료를 돌린 숫자로. 못 쟀으면 미확인)
   - 입력을 받아 결과가 저장되기까지 어느 모듈·저장 상태를 어떤 순서로 거치나 (모듈마다 맡는 일)
   - 규칙을 지킨다는 것을 어떤 경로로 확인하나 — 구현된 확인 장치와, 하지 않았거나 가정으로 남긴 것(검사기가 내 결정을 계획 코드와 같은 해석으로 판정하는 곳 포함)을 나눠서
   - 동시에 실행되거나, 도중에 오류가 나거나, 취소되면 기존 결과와 저장 상태는 어떻게 되나 — 저장이 둘 이상으로 나뉜 곳과 그 사이에서 끊기면 남는 행을 읽는 화면, 상태를 바꾸는 요청이 대상을 id 로 받는지 '그 순간 최신'으로 고르는지, 이미 공개·적용된 이전 결과가 새 입력과 섞이는 곳, 일부러 실패를 일으켜 본 근거(없으면 미확인)
   - 조건(문턱·정원·기간·경계에 걸친 대상)을 바꿔 다시 돌리면 어디가 깨질 수 있나 — 같은 판정을 두 곳 이상에서 따로 계산하는 곳 포함, 조건 하나를 규칙을 못 지킬 만큼 바꿔 돌렸을 때 막히는지·저장·공개되는지를 명령과 숫자로(못 돌렸으면 미확인)
   - 이 숫자는 어떻게 나왔나 / 요청과 다르게 간 곳은 어디인가 (사용자 결정·요청자 미확인 포함)

   질문마다 아래 모양으로. 칸은 문장이 아니라 짧은 명사구.
   ```
   Q3. 취소 건은 왜 합계에서 아예 뺐나요?
     근거: calc.py:42 (# 규칙 4) · 커밋 a1b2c3d · NOTES 요청자 대화 10:14
     지점: 취소 3건 제외
     왜:   요청자 10:14 "취소는 이용으로 안 본다" / 차감안은 기각(합계가 음수 됨)
     다음: 취소 뒤 재예약 같은 경우는 미확인 → 요청자 확인
   ```
   코드 근거는 함수 이름이 아니라 `파일:줄`로 쓴다. 좌표는 적기 전에 그 줄을 열어 말과 맞는지 보고, 기준·규칙이면 그 값이 실제로 쓰이는 호출부까지 따라간다(정의만 있고 안 쓰이면 '근거 없음'). '지점'·'왜' 칸의 숫자와 '한 번에·전부' 같은 단언도 줄이나 명령이 없으면 "근거 없음". 근거가 없는 답은 뼈대에 넣지 않는다.

2. **외울 숫자 5개.** 결과물의 핵심 숫자와 그 숫자를 만든 명령. 명령은 지금 다시 돌려 값이 같은지 확인한 뒤 적는다.
   ```
   - 대상 120건 ← python3 calc.py --count
   ```

3. **전제가 틀린 질문 대비 2~3개.** 다 된 것처럼 보이지만 확인하지 않은 것, 만들지 않은 기능, 요청과 다르게 간 곳을 누가 "이미 된 것"으로 전제하고 물을 때. 질문 예와 바로잡는 첫 문장 틀:
   ```
   - "주말 건도 반영됐죠?" → 실제로는 평일만 구현했습니다. 주말은 '이번엔 안 함'(요청자 10:20 합의)입니다.
   ```

4. **모를 때의 틀.** 확인하지 않은 것을 물으면:
   ```
   그 부분은 확인하지 못했습니다. 확인하려면 ○○를 돌려 △△와 비교하겠습니다.
   ```
   남은 한계 가운데 이 틀로 답해야 할 것을 2~3개 골라 ○○·△△를 채워 둔다.

## 하지 않는 것

- 질문에 대한 완성된 답 문장을 쓰지 않는다(사용자가 자기 말로 말한다)
- 근거 없는 이유를 만들어 넣지 않는다
- 문서를 고치지 않는다. 0번 '지금 고칠 것'은 목록만 내고, 고칠지는 사용자가 정한다

마지막 줄: `직접 확인: 화면을 보지 않고 질문마다 소리 내어 한 문장씩.`
