# 계획서

> 평소의 /계획서 는 고치기 전에 근거를 HTML 한 장으로 만든다: 원인을 브라우저에서 재고(계산된 스타일, 시안의 실측값), 지금 화면과 고친 뒤 화면(고친 뒤는 CSS 주입으로 흉내 냈다고 밝힘) 캡처, 원인 그림, 코드 수정 방향. 코드는 고치지 않는다. 여기서는 데이터·도구 작업이라 PLAN.md 와 view/plan.html(다시 정의한 문제, 흐름, 규칙이 걸린 단계, 확인받지 않은 것)로 '내 이해와 에이전트의 이해가 같은지'를 대조한다.

README 가 계획 문서 이름·위치를 정했으면 그것을 쓴다. 아니면 `PLAN.md`.

```
# PLAN

## 다시 정의한 문제
요청자가 처음 한 말 → 대화 뒤 내 말. 두세 문장. 요청자 시각을 단 말에는 요청자가 한 말만 넣고, 내가 정한 기준(줄인다·최소로)은 `(내 결정)`을 붙여 따로 쓴다. 누가 언제 무엇을 결정하는 데 쓰는가(대화에 없으면 [추정] 을 달고 물으라고 알린다).

## 완료 조건
| 조건 | 확인 방법(명령 또는 화면) |

## 우선순위
- 먼저: …  (규칙 번호)
- 시간이 남으면: …
- 이번엔 안 함: …  (이유. 요청자가 빼라고 하지 않은 것은 '제안'이라고 적고, 결과를 보여 주는 메시지에서 묻는다)

## 단계
1. 무엇 (이 단계가 바꾸는 행: 지금 N건) — 확인: `명령` → 기대 결과

## 규칙 ↔ 단계
규칙 1·2 → 단계 1 / 규칙 3 → 단계 2 … (이어지지 않은 규칙은 여기에 따로)

## 예시 한 건
- 입력: (파일:줄) 한 줄 그대로
- 적용하는 규칙: 규칙 n → 이렇게 바뀜
- 기대 출력: 결과물의 그 줄·칸
```

- '먼저'에는 요청 문서(README 등)가 필수로 정한 기능·산출물을 빠짐없이 넣는다. 요청자 대화에서 나온 추가 기능은 '시간이 남으면'에. 요청 문서에 없는 기능을 '먼저'에 두려면 이유(출처: 요청자 HH:MM)를 단다.
- 완료 조건은 숫자나 눈으로 볼 수 있는 행동으로. "잘 동작한다" 는 쓰지 않는다.
- 완료 조건 중 하나 이상은 **코드와 독립으로 낸 기대 숫자**(원문에서 손으로 센 값, 다른 방법으로 다시 센 값, 한 건의 손계산)와 비교한다. 독립 계산 명령은 PLAN 에 그대로 적거나 커밋되는 `checks/` 에 둬서 누구나 다시 돌릴 수 있게 한다. 결과끼리 맞는지만 보는 확인(행 수 = 행 수, A 파일 = B 파일)은 규칙이 틀려도 통과한다. 검사기는 규칙 문장을 계획 코드와 같은 해석으로 옮기지 않는다 — 두 가지로 읽히면(경계 값 포함 여부·끝수 처리 포함) 엄격한 쪽으로 세고, 다른 쪽으로 읽었을 때 달라지는 건수를 검사기 출력에 한 줄씩 찍는다.
- 확인 명령은 결과의 내용을 세거나 비교해야 한다. 파일이 있는지(`test -f`)·오류 없이 끝났는지만 보는 확인은 쓰지 않는다.
  예: "빨간 칸 수 = 판정 이탈 수", "메일 속 대상 = 이탈 대상 (`diff` 출력 없음)", "손계산한 한 건 = 출력의 그 줄"
- 빈 파일·빠진 칸·처음 보는 값·참조표에 없는 ID 처럼 자료가 틀어진 경우를 검증용 사본으로 만들어 확인하는 단계를 하나 넣는다(결과가 '이상 없음'으로 잘못 나오는지). 사본과 그 결과는 `.verify/` 처럼 git 이 무시하는 폴더에 두어 진짜 결과물을 덮어쓰지 않게 한다. 확인은 경고가 나오는지만 보지 말고 사본마다 요약 숫자를 원본과 나란히 적어 터무니없는 값이 없는지 본다.
- 요청자가 이유를 댄 규칙("평균이 튀어서", "따로 세면 숨어서")은 그 이유를 보여 주는 숫자를 결과물에 한 줄 넣는 단계를 둔다(평균 vs 중앙값, 묶기 전 vs 후 건수). 요청자가 결과를 보고 규칙이 맞았는지 알 수 있게.
- 원인을 비교하는 결과물이면, 한 후보의 효과를 다른 후보를 뺀 묶음으로 다시 재는 확인을 하나 넣는다(두 후보가 겹쳐서 둘 다 원인처럼 보이는지 가르기 위해).
- 파이프(`|`)가 든 확인 명령은 표 칸에 넣지 말고 단계 목록이나 코드 블록에 쓴다.
- 정확도·기준값을 재는 단계가 있으면, 기준을 정할 때 볼 사례와 잴 때만 쓸 사례를 계획에서 미리 나눈다.
- 단계마다 그 단계가 바꾸는 행이 지금 자료에 몇 건인지 적는다. 0건이면 구현 전에도 확인이 통과하니, 그 경우를 담은 검증 사본을 확인에 넣는다.
- 단계는 한 번에 끝낼 크기로 4~6개. 판정·계산 먼저, 화면·꾸밈은 나중.
- 확정된 규칙마다 어느 단계에서 다루는지 '규칙 ↔ 단계'에 번호로 잇는다. `(코드 아님)` 규칙은 어떻게 지키는지(작업 순서·메시지) 적는다.
- 단계의 기대 결과는 요청자와의 마지막 합의 문답(NOTES '요청자 대화')과 한 줄씩 맞춰 본다. 다르거나 근거가 없으면 [추정].
- 근거 없는 내용은 [추정]. 아직 없는 옵션·출력 형식을 가정한 확인 명령에도 [추정] 을 달고, `$구현` 이 실제 형식으로 고쳐 같은 커밋에 넣는다.

PLAN 을 쓴 뒤 AGENTS.md '목표'의 자리표시 줄(`(누가) (언제) …`, `비어 있으면 …`)을 지우고 다시 정의한 문제와 완료 조건으로 채운다(비어 있으면 `$구현` 이 멈춘다).
그다음 그림으로 대조한다: `python3 .agents/skills/계획서/scripts/plan_html.py` (없으면 `~/.agents/skills/계획서/scripts/plan_html.py`) → `view/plan.html`. 보는 법: 새 터미널에서 `python3 -m http.server 8090 --bind 0.0.0.0` → Browser 탭 PORT 8090, URL `/view/plan.html`. 사용자에게 "오른쪽(대화 뒤 내 말) · 규칙의 맡은 곳 · 확인받지 않은 것이 내 생각과 같은지 보고, 다르면 말로 고치라"고 알린다. PLAN 이 바뀔 때마다(이 스킬, `$요구` 5번, `$구현` 커밋 전) 다시 돌린다.
그다음 PLAN.md · AGENTS.md · NOTES.md · .gitignore · checks/ · view/plan.html 을 `계획: 다시 정의한 문제 한 줄` 로 커밋한다.

쓰고 나면 멈춘다. 마지막 줄: `직접 확인: '다시 정의한 문제'를 내 말로 고치고, 우선순위가 요청자와 합의한 순서인지.`
