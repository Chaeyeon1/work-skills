# 요청 파악 (만들지 않는다)

> 평소에는 요청을 받으면 기능 문서에 기획·맥락부터 쌓는다(기능별 문서에 덧붙이는 커맨드). 이 스킬은 거기에 '요청자에게 무엇을 물어야 하나'를 자료 근거와 함께 뽑는 단계를 더한 것이다.

코드는 만들지 않는다. 문서는 둘만 건드린다:
- `NOTES.md` 가 없으면 아래 뼈대로 만들고 '진행' 첫 줄에 지금 시각(`date +%H:%M`)을 적는다.
- 아래 3·4번에서 찾은 것 중 아직 답이 없는 것을 AGENTS.md '확인 안 된 것'에 **한 줄에 하나씩** `- [파악] 무엇 — 물어볼 것` 으로 넣는다(이상한 점 표의 행마다 따로, 기본 질문 줄에 합치지 않는다. 한 줄에 물음 하나). 기본 질문 셋과 먼저 물을 3개에는 `★`(아래 5번). 짚고 넘어간 것이 대화 중에 사라지지 않게 하기 위해서다.

```
# NOTES
## 요청자 대화
## 진행
- HH:MM 시작
## 결정
## 확인
## 남은 한계
```

## 순서

1. **요구 사항.** README·요청 문서에서 산출물·파일 이름·위치·형식·실행 방법·하면 안 되는 것. 없으면 "지정 없음".
2. **자료 훑기.** 파일마다 크기부터(`wc -l`). 50줄 이하는 통째로 읽고, 큰 파일은 앞부분(`head`)과 필요한 곳만. 이름이 비슷한 파일(버전·변경본·사본)은 `diff` 로 서로 비교한다. 큰 파일을 통째로 읽지 않는다. 표 자료는:
   - 열 이름, 값의 종류, 빈칸, 단위, 시각 형식, 비고란
   - 중복(ID 열을 뺀 나머지가 같은 줄, 묶음마다 같은 값이 되풀이되는 집계 열도)
   - 기록·실적 자료면 행이 없는 것이 무슨 뜻인지(안 함·못 함·기록 안 됨). 실적에 쓴 기록은 관행이지 규칙이 아니다
   - 짝으로 된 값(A→B·B→A)이 방향마다 다른 쌍 수
   - 쓰는 자원(사람·장소·장비)마다 '못 쓰는 때' 열이 있는지, 정원 같은 상한을 끝까지 채워도 되는지(없으면 '늘 쓸 수 있다고 가정'·'상한까지 채워도 된다고 가정'을 이상한 점 표에 한 행씩)
   - 어느 출발점에서도 멀거나 늦는 대상 수(있으면 '지금 그 대상은 어떻게 하나'를 물을 것 후보로)
3. **이상한 점 표.** NOTES '진행' 아래 `### [HH:MM] 이상한 점` 에 남긴다. `| # | 어디(파일:줄 또는 열) | 본 것 | 물어볼 것 | 답에 따라 바뀌는 것 |`
   - 자료끼리, 요청 문서와 자료가 서로 다른 말을 하는 곳을 맨 위에
   - 이름이 다른 파일(변경본, 예전 버전, 메모), 끝났거나 진행 중인 건, 같은 대상이 두 번 나오는 곳, 자료 기간·교대·마감 같은 경계 바로 밖이나 걸친 줄
   - 물어볼 것은 대상 하나 + 구체 상황 + 열린 질문. 내 해석이나 예상 답을 질문에 담지 않는다(요청자가 그대로 받아들인다). 예: "주문서와 송장의 수량이 다른 건은 어느 쪽을 기준으로 보시나요?"
   - 끝이 "~하나요?", "~할까요?", "~인가요?" 로 예/아니오가 나오는 문장은 "어떻게 / 어느 쪽 / 언제부터 / 어떤 경우에" 로 고쳐 쓴다.
     나쁨: "수정본을 우선 적용하나요?" → 좋음: "원본과 수정본 내용이 다를 때 어느 쪽 기준으로 보세요?"
   - 답에 따라 바뀌는 것은 건수·판정이 어떻게 달라지는지 한 줄
4. **정해지지 않은 말.** "적절히", "주요", "정리" 처럼 기준·기간·대상이 빠진 말, 요청 문서 규칙에서 '그·해당·각'이 가리키는 대상이 둘로 읽히는 곳(읽는 방식마다 걸리는 건수). 물어볼 것을 단다. "감사 전", "연말", "다음 회의 때" 같은 시점 말은 **날짜로** 묻는다(기준일 뒤에 생기는 일 — 곧 만료·곧 마감 — 이 거기서 드러난다). "감사·점검·정산·보고"처럼 기간을 전제하는 말은 기준일과 따로 **대상 기간(시작·끝·시간대)**을 묻는다(★ 후보). 자료가 그 기간·달·분기 경계를 넘으면 넘친 줄 수를 붙인다.
5. **먼저 물을 것.** 기본 질문 셋은 언제나 ★ 맨 위에 `[파악]` 줄로 둔다: "이 결과를 누가 언제 어디서 쓰나", "지금은 이 일을 어떻게 하나"(시간이 드는 곳은 답을 들은 뒤 따로)(다시 정의한 문제가 여기서 나온다), "이 결과를 보고 누가 누구에게 무엇을 하나"(그때 손에 있어야 할 것은 답을 듣고 꼬리로)(두 번째 결과물이 여기서 나온다). 그 밑 ★ 3개: 첫째는 늘 '어떤 시간대·경우에 쓸 수 없거나 혼자 하면 안 되는 사람·장소·장비가 있나', 나머지 둘은 자료만으로 뜻을 정할 수 없는 업무 사실 가운데 결과를 가장 크게 뒤집는 것(시점 말·대상 기간 줄도 여기서 고른다. 설계 판단은 요청자에게 묻지 않고 `$논의`). ★ 는 기본 셋 + 3개, 모두 6줄까지.

자료에서 확인되는 사실은 묻지 않고 확인해서 적는다. "뭘 만들면 되나요" 같은 넓은 질문, 해법이 들어간 질문은 넣지 않는다. 요청자가 지금 어떻게 하는지 말하게 묻는다.

끝나면 NOTES·AGENTS 를 `파악: HH:MM` 으로 커밋한다.

마지막 줄: `직접 확인: ★ 기본 셋부터 내 말로 하나씩 물어보기. 꼬리 질문은 답을 듣고. 남은 [파악] 줄은 합의 확인 메시지에 넣거나, 안 물으면 '남은 한계'로 옮긴다.`
