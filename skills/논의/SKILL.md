# 방향 논의 (코드 미생성)

> 평소의 /논의 는 분석만 하고 코드는 만들지 않는다. 프로젝트 안의 비슷한 코드, 프로젝트 규칙, 업계 사례를 세 갈래로 동시에 조사해 비교표와 추천을 낸다. 여기서는 작업 폴더가 작아 자료·확정된 규칙 기준으로 비교하고, 고른 것과 기각한 것을 기록에 남기는 데 무게를 둔다.

인자: 논의 주제. 사용자가 고민 중인 선택지가 있으면 그것부터.

1. **지금 상황.** 관련 파일·자료를 필요한 만큼만 본다. 코드가 아직 없으면 바로 2.
2. **선택지 비교.**

| | A | B | C |
|---|---|---|---|
| 설명 | | | |
| 확정된 규칙을 지키나 | 규칙 번호로 | | |
| 만드는 데 드는 것 | | | |
| 틀릴 수 있는 곳(나눠 푸는 안이면 앞 단계가 모르는 뒤 단계 제약, 뒤 단계가 실패할 때 대상이 가는 곳) | | | |
| 확인 방법 | | | |

3. **추천.** 하나를 고르고 근거를 규칙 번호·자료(파일:줄)로. 재지 않은 것은 [추정].
4. 사용자가 고르면 NOTES.md '결정'에 `- HH:MM 고른 것 / 이유 / 기각한 것과 이유 — 출처: HH:MM 나`, 기각한 것은 AGENTS.md '기각한 대안'에도 한 줄. 사용자의 선택은 요청자 규칙이 아니다. 이 선택으로 정해진 '확인 안 된 것' 줄이 있으면 끝에, 없으면 새 줄을 만들어(기준의 순서·무게 포함) `→ 사용자 결정 HH:MM (요청자 미확인)` 을 단다. 요청자가 맡긴 줄도 지우지 않고 같은 표시를 단다.

기록한 NOTES·AGENTS 를 `논의: HH:MM 고른 것` 으로 커밋한다.

고른 것이 비교 기준이면, 기준 항목 번호를 모두 적고, 요청자가 문턱을 말하지 않은 번호마다(도착·대기처럼 상대편이 느끼는 시간 포함) '어디서부터 불편해하나'를 묻는 보낼 말을 한 줄씩 낸다(낸 줄 수 = 문턱 없는 번호 수). 가장 단순하게 요구를 채우는 안을 늘 후보에 넣고, 고른 안과 같은 기준·같은 대상으로 잰 숫자와, 기준이 둘 이상이면 첫째·둘째 순서를 바꿔 돌린 숫자를(실패하거나 빠진 대상이 있는 안은 그 대상을 뺀 지표 대신 실패 건수와 전체 대상으로 센 값을) 다시 돌릴 명령(커밋되는 `checks/` 등에 둔 것. git 이 무시하는 폴더는 안 된다)과 함께 NOTES '결정'에 남긴다. 그 명령을 처음 돌리면 기각 이유의 [추정]을 잰 값으로 바꾼다(결정 줄과 '기각한 대안' 줄 모두, 이유가 뒤집히면 실제 차이로).

시각(HH:MM)은 `date +%H:%M` 으로 찍는다.
